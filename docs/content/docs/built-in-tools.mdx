# Built-in Tools Reference

The built-in tools in `bricks::tools::all()` are in the categories below, and each is available through the composition functions in `bricks::tools`. `CodeSearch` is not in those sets (add `CodeSearchTool::with_embeddings` when embeddings are configured), `shell()` and `shell_with_jobs()` expose only the platform-native shell (`Bash` and `Job` on Unix, `PowerShell` on Windows), and `Skill` is added by an agent with a skills service. The sub-agent tools (`Agent`, `Managent`, `Messagent`) are not in those sets either: see [Sub-agent tools](#sub-agent-tools).

```text
bricks::tools::all()                     // coding() + planning() (13 on Unix, 12 on Windows)
bricks::tools::coding()                  // filesystem() + shell_with_jobs() + web() (12 on Unix, 11 on Windows)
bricks::tools::filesystem()              // 8 tools
bricks::tools::shell()                   // Bash on Unix (no job registry), PowerShell on Windows
bricks::tools::shell_with_jobs(registry) // Bash and Job on Unix, PowerShell on Windows
bricks::tools::web()                     // 2 tools: WebFetch, WebSearch
bricks::tools::planning()                // 1 tool: TodoWrite
```

`all()` and `coding()` put `Bash` and `Job` on a registry of their own. An agent
built with a session's registry puts them on it; see
[Background Tasks](/docs/background-tasks) and [bricks-tools](/docs/api-tools).

## Filesystem

### Read

Read a text file (with optional line offset and limit) or an image file (PNG, JPEG, GIF or WebP). For text files, returns content with line numbers. For images, the type is read from the file's bytes, and the model receives the image itself (up to 3,750,000 bytes and 8,000 pixels on a side; see [Multimodal Input](/docs/multimodal#images-returned-by-tools)). A relative `file_path` resolves against the working directory.

**Permission:** ReadOnly

<TypeTable
  type={{
    file_path: {
      type: 'string',
      description: 'Path to the file, absolute or relative to the working directory.',
      required: true,
    },
    offset: {
      type: 'integer',
      description: '1-based line number to start reading from (default 1; 0 also starts at line 1).',
    },
    limit: {
      type: 'integer',
      description: 'Number of lines to read.',
      default: '2000',
    },
  }}
/>

**Permission:** Write

### Edit

Replace text in a file, with one replacement (`old_string`, `new_string`) or several (`edits`). Several replacements are applied in order, each against the result of the previous one, and the file is written only if all of them apply. Fails if an `old_string` is not unique (unless `replace_all` is true). No `Read` is needed first: the change is decided on what it would do to the file. The file is written under a per-file lock, and not at all if it changed after its change was approved (the call is then decided again). Replaces the former `MultiEdit`, which no longer exists.

**Permission:** Write

<TypeTable
  type={{
    file_path: {
      type: 'string',
      description: 'Absolute path to the file.',
      required: true,
    },
    old_string: {
      type: 'string',
      description: 'One replacement: the text to find. Use with new_string, not with edits.',
    },
    new_string: {
      type: 'string',
      description: 'One replacement: the replacement text. Omit it, or give an empty string, to delete old_string.',
    },
    replace_all: {
      type: 'boolean',
      description: 'Replace all occurrences instead of requiring uniqueness.',
      default: 'false',
    },
    edits: {
      type: 'array',
      description: 'Several replacements, in order: entries of { old_string, new_string?, replace_all? }. Use instead of old_string, new_string and replace_all, not with them. Non-empty.',
    },
  }}
/>

### CodeStats

Count the code, comment and blank lines of a file or a directory tree, in total, per language or per file (Tokei, in process, no external program). The walk follows `.gitignore`, `.ignore` and `.tokeignore`, nested, and counts hidden files. Directory links are not followed.

**Permission:** ReadOnly

<TypeTable
  type={{
    path: {
      type: 'string',
      description: 'File or directory, relative to the working directory.',
      default: 'working directory',
    },
    detail: {
      type: 'string',
      description: '"summary" (totals only), "languages" (one row per language) or "files" (one row per file).',
      default: 'languages',
    },
    language: {
      type: 'string',
      description: 'Count only the files of this primary language, as Tokei names it (`Rust`, `TypeScript`, `Jupyter Notebooks`). Any case; an unknown name is an error.',
    },
    top_n: {
      type: 'integer',
      description: 'Rows shown, from 1 to 100, sorted by code lines. It limits the rows only, never the analysis.',
      default: '20',
    },
    exclude: {
      type: 'array',
      description: 'Gitignore-style globs, relative to the analysed directory. Exclusions only: a `!` pattern is refused.',
    },
  }}
/>

The result is JSON: `totals` (`files`, `code`, `comments`, `blanks`, `lines`), `results`, `truncated`, `omitted`, `partial` and `warnings`. Totals always cover the whole analysis, and `omitted` counts the rows not shown. `partial` is `true` when something expected was not counted (an unreadable file, a file changed during its read, an invalid notebook, a walk error, an overflow): check it before presenting the totals as complete. Lines are Tokei's counting units, not `wc -l`; a shebang line counts as a comment. A file counts for its primary language, with the blocks it embeds (HTML with JavaScript counts as HTML).

A `.tokeignore` file at the root of the tree, with the same syntax as `.gitignore`, is the way to leave out generated folders such as `target/`, `node_modules/`, `dist/` or `coverage/`. Bricks never creates it.

## Shell

### Bash

Execute a shell command. Each call is its own process, started from the session's state. When it ends normally, its working directory, exported variables, functions and aliases persist for the next calls; commands of a session run side by side.

**Permission:** Execute

<TypeTable
  type={{
    command: {
      type: 'string',
      description: 'The bash command to execute.',
      required: true,
    },
    timeout: {
      type: 'integer',
      description: 'Timeout in milliseconds (default 120000, max 600000). With `background: true` and `ready_pattern`, milliseconds to wait for readiness (default 10000).',
      default: '120000 (max 600000)',
    },
    background: {
      type: 'boolean',
      description: 'Start a background job at once; the result gives its job_id. Follow it with Job.',
      default: 'false',
    },
    ready_pattern: {
      type: 'string',
      description: 'Background only. A regex on output lines: the job is ready when a line matches.',
    },
    input: {
      type: 'string',
      description: 'Text given to the command on stdin. Empty stdin by default.',
    },
  }}
/>

<Callout>
Bash calls are decided by the session policy at the `Execute` level, whatever the command. No analysis of the command runs before it and none lowers or raises that level. The AST analysis of `bricks_tools::tool_primitives::bash_safety` is an SDK primitive a caller can use on its own; see [Code intelligence](/docs/code-intelligence#bash-command-safety-analysis).
</Callout>

A `background: true` command is recorded by the session's job registry. Without one, as with `bricks::tools::shell()`, `background: true` is refused before it starts while foreground commands still run. A job is followed with [Job](#job).

### Job

The calling agent's background jobs, started with `Bash` and `background: true`. Each job is visible only to the agent that started it. Running is not ready, and ready is not proof that a service works. Stopping a job ends its process group and tree (TERM, then KILL). See [Background Tasks](/docs/background-tasks).

**Permission:** Execute for `stop`; ReadOnly for `list`, `status`, `output` and `wait`.

<TypeTable
  type={{
    action: {
      type: '"list" | "status" | "output" | "wait" | "stop"',
      description: 'What to do. `list` gives your jobs; the other actions need a `job_id`.',
      default: 'list',
    },
    job_id: {
      type: 'string',
      description: 'The job, for every action but list. Given by Bash.',
    },
    stream: {
      type: '"stdout" | "stderr"',
      description: 'For output.',
      default: 'stdout',
    },
    offset: {
      type: 'integer',
      description: 'For output: the 0-based line to start at. Not with tail.',
      default: '0',
    },
    limit: {
      type: 'integer',
      description: 'For output: lines to return, from 1 to 2000.',
      default: '200',
    },
    tail: {
      type: 'boolean',
      description: 'For output: the last `limit` lines. Not with offset.',
      default: 'false',
    },
    timeout_ms: {
      type: 'integer',
      description: 'For wait: from 1 to 600000. A timeout stops nothing.',
      default: '60000',
    },
  }}
/>

Unknown fields and out-of-range values are refused. `output` returns a header (the range, the complete lines, the bytes received, what is no longer in memory, the raw log path and the next offset), then the lines without numbers. A line longer than the page is cut and marked, and the offset moves past it. A line still in progress is shown apart and does not move the offset.

## Planning

### TodoWrite

Create and update the plan of the conversation: the complete list of its steps, with status tracking. The plan is kept with the conversation (`plan.json` in its files folder), shown to the user, and restored when the conversation is reopened.

**Permission:** None

<TypeTable
  type={{
    todos: {
      type: 'array',
      description: 'The complete updated list of steps. An empty list clears the plan.',
      required: true,
    },
    'todos[].content': {
      type: 'string',
      description: 'Task description in imperative form ("Fix the tests").',
      required: true,
    },
    'todos[].status': {
      type: '"pending" | "in_progress" | "completed"',
      description: 'Current task state.',
      required: true,
    },
    'todos[].activeForm': {
      type: 'string',
      description: 'Present continuous form ("Fixing the tests").',
      required: true,
    },
    explanation: {
      type: 'string',
      description: 'Optional: why the plan changed (a step added, dropped or blocked).',
    },
  }}
/>

- At most one step may be `in_progress`. An invalid update is refused with an error, and the previous plan stays.
- Each accepted update takes the next revision, clearing included.
- A conversation has its own plan. A sub-agent never shares its parent's; a sub-agent that has TodoWrite keeps its own plan in memory.

## Sub-agent tools

`Agent` (one mission with `prompt`, or up to 16 with `missions`), `Managent` (status, waiting, results, resumes, cancellation, and ChangeSets), and `Messagent` (internal mail between agents in a session) are native tools. The CLI and the controller register them when `[agents] enabled` is true (the default). They are not in `bricks::tools::all()`.

Available profiles (`general`, `explore`, plus custom `.bricks/agents/*.md` and `~/.bricks/agents/*.md` profiles) are loaded dynamically and listed directly in the `Agent` tool description.

`Agent` parameters: `profile` (default `"general"`), `description` (3 to 5 word UI label), `prompt` (with `task` accepted as an alias), `model`, `effort`, `fork` (default `false`), `isolation` (`"shared"` or `"worktree"`), and `missions` (1 to 16 mission objects).

Sub-agents always run in parallel. `Agent` returns their ids at once; `Managent wait` and `result` give the results.

**Permission:** `Agent`: Execute. Allowing it allows that delegation only. A child's own calls follow the same policy: a call the policy would ask is allowed for the child, because launching it was the approval, while refusals still hold. A profile's `permissions` can narrow this (see `docs/agents.md` in the repository). `Managent`: ReadOnly for `list`, `status`, `result`, `wait`, `inspect_changes`, and `check_changes`; Execute for `resume`, `cancel`, and `rebase_changes` with `verify_cmd`; Write for `apply_changes`, `discard_changes`, and `rebase_changes` without `verify_cmd`. `Messagent`: ReadOnly.

The `Managent` actions, by their parameters:

| action | parameters | effect |
|---|---|---|
| `list` | none | lists visible sub-agents with `agent_id`, `description`, `profile`, `state`, `elapsed_ms`, `last_action`, ChangeSet id and state, and slot counts |
| `status` | `agent_id` | shows the same enriched status for one sub-agent |
| `result` | `agent_id` | returns the sub-agent's final summary, changed files, commands run, and warnings |
| `wait` | `mode` (`"any"` or `"all"`), `agent_id` or `agent_ids`, `timeout_ms` (default 60000, max 600000) | waits for sub-agents and returns `finished` and `pending` entries; a timeout cancels nothing |
| `resume` | `agent_id`, `prompt` | resumes an ended sub-agent in its own conversation with a new prompt |
| `cancel` | `agent_id` | requests cancellation of `agent_id` and its descendants |
| `inspect_changes` | `changeset_id` or `agent_id` | shows changed files and patch diff for an isolated worktree ChangeSet |
| `check_changes` | `changeset_id` or `agent_id` | checks whether the ChangeSet applies cleanly without writing files |
| `rebase_changes` | `changeset_id` or `agent_id`, optional `verify_cmd` | rebases the ChangeSet onto `HEAD` in a temporary worktree and optionally runs `verify_cmd` |
| `apply_changes` | `changeset_id` or `agent_id` | applies the ChangeSet to the working tree without committing |
| `discard_changes` | `changeset_id` or `agent_id` | discards the ChangeSet and removes its worktree while keeping its patch record |

Their parameters, the limits (`max_depth` = 1, `max_concurrent` = 16, `max_queued` = 64, `admission_timeout_ms` = 60000, `summary_chars` = 30000), and the isolation rules are in `docs/agents.md` in the repository.

### Messagent

Team mail between the agents of a session: `send`, `read` (new messages, or the whole thread with `all`), and `members`. It is a native tool registered with the agent runtime, outside `bricks::tools::all()` (see [Sub-agent tools](#sub-agent-tools)).

Recipients read a message between two turns, after the tool calls of the turn in progress; a message never interrupts a running command. A message does not restart an ended sub-agent. Refusals are explicit (unknown recipient, empty content, over 16 KiB, 32 messages already waiting for a recipient); nothing is reported as sent when it was not. Without an agent runtime in the session, nothing is sent or read.

**Permission:** ReadOnly

<TypeTable
  type={{
    action: {
      type: 'string',
      description: '"send", "read" or "members".',
      required: true,
    },
    to: {
      type: 'string | string[]',
      description: 'send: `main`, a sub-agent id (`sub_0000`), a list of ids, or `"team"`.',
    },
    content: {
      type: 'string',
      description: 'send: the message, 16 KiB at most.',
    },
    reply_to: {
      type: 'string',
      description: 'send: the id of the message answered (`m0001`).',
    },
    all: {
      type: 'boolean',
      description: 'read: the whole thread instead of the new messages.',
    },
  }}
/>

## Other

### Skill

Activates an [Agent Skill](https://agentskills.io/specification) (reads its full instructions), lists the skills the agent may activate, locates one of a skill's files, checks a skill folder (`validate`) or installs one in Bricks' store (`install`). Activating runs nothing and grants no permission. Present only on agents built with a skills service (`AgentBuilder::skills`; the `bricks` CLI does it).

**Permission:** ReadOnly, except `install`, which writes in the store and asks the write permission.

<TypeTable
  type={{
    action: {
      type: 'string',
      description: '"activate" (default when `skill` is given), "list", "resource", "validate" (checks the folder at `path`, writes nothing) or "install" (copies it into the store, validates the copy and publishes it; the folder is left as it was). `skill: "list"` without an action lists.',
    },
    skill: {
      type: 'string',
      description: 'The skill name, exactly as listed.',
    },
    args: {
      type: 'string',
      description: 'The request to apply the skill to; returned separately, never substituted into the instructions.',
    },
    query: {
      type: 'string',
      description: 'For "list": words to filter names and descriptions (20 per page, `page`).',
    },
    path: {
      type: 'string',
      description: 'For "resource": a path relative to the skill\'s directory. For "validate" and "install": the skill folder, relative to the working directory.',
    },
  }}
/>

See `docs/skills.md` in the repository for sources, the store, activation, withdrawal and limits.
